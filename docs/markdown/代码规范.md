`.clang-format` 的覆盖项（其余继承 LLVM）：

```yaml
IndentWidth: 4
ColumnLimit: 100        # ← 新定；本规范原先没有行宽要求
PointerAlignment: Left
BreakBeforeBraces: Attach
NamespaceIndentation: None
AllowShortFunctionsOnASingleLine: Inline
IndentPPDirectives: BeforeHash
```

`ColumnLimit: 100` 是本次新增的约束：§5.1 只限制了函数行数，从未限制行宽，而 `clang-format` 必须知道一个列宽才能工作。这一项**由 `pre-commit` 强制执行**（`.clang-format` 是唯一真源，改它等于改门禁）。

`IndentPPDirectives: BeforeHash` 是 2026-11-01 新增（#54 期间）：`client/common/API.h` 的嵌套 `#if` 一直按 4 空格缩进书写，而 LLVM 默认的 `None` 要求 `#` 顶格；要保留这种缩进就只能把规则写进 `.clang-format`。影响面很小：全仓 69 个非 `vendor` 的 C/C++ 文件里只有 5 个在该规则下会被重排（`API.h` 已是目标形态，其余 4 个是 `VideoEngine.h` 与 3 个 Flutter runner 文件），它们下次被改动时由 `pre-commit` 顺带格式化即可。

## 1. 命名规范

### 1.1 类名、结构体名、枚举名、文件名

使用 **驼峰命名法** (PascalCase)，首字母大写。

```cpp
// 正确
class AudioEngine { };
struct AudioSyncInfo { };
enum class SyncState { };

// 错误
class audio_engine { };
struct audio_sync_info { };
```

> **沿革**：2026-06-06 之前本规范与 2026-05-25 冻结的 `代码规范.docx`（曾归档于 `docs/archive/`，该目录已于 2026-11-02 删除）都曾规定**文件名用蛇形命名法**，后改为 PascalCase。以当前规范为准 —— 代码实测一致：`client/` 下 51 个被跟踪的 `.h/.cpp` 中 50 个是 PascalCase，**唯一例外是 `pch.h`**（`practice/` 不在版本控制里，磁盘上现在只剩 `AudioDecoder.h`）。此前记的「55 个中 51 个、4 个例外」是按 2026-10-09 的磁盘状态数的，12 个 `tmp.*` 占位文件已于 2026-10-11 删除。

### 1.2 函数名、变量名

使用 **蛇形命名法** (snake_case)，全小写加下划线。

```cpp
// 正确
bool set_play_speed(float speed);
int student_age;
void init_audio_engine();

// 错误
bool setPlaySpeed(float speed);
int studentAge;
void initAudioEngine();
```

### 1.3 宏、常量

使用 **全大写 + 下划线**。

```cpp
#define MAX_SIZE 1024
#define PI 3.14159

const int DEFAULT_PORT = 8080;
```

### 1.4 命名空间

使用 PascalCase，项目根命名空间为 `Prism`，子命名空间按模块划分。

```cpp
namespace Prism::Engine { }
namespace Prism::Business { }
namespace Prism::Service { }
namespace Prism::Server { }     // Server 端代码
```

> ⚠️ `server/` 自 2026-11（#147 / #150）起已有实现，`Prism::Server::{Adapter,Business,Network}` 三个子命名空间分别由 server/{adapter,business,network} 使用；新增 Server 端代码继续遵循 `namespace Prism::Server { ... }` 结构。

### 1.5 简写约定

使用大众熟知和默认约定的简写，不自行创造。

```cpp
// 正确（公认简写）
int max_size;      // maximum
int user_id;       // identifier
uint64_t pts;      // presentation timestamp

// 错误（自创简写）
int mx_sz;
int usr_idfr;
```

## 2. 注释规范

### 2.1 API 接口注释

使用 **Doxygen 风格**（类似 JavaDoc），函数或复杂设计必须在前面添加注释。

```cpp
/**
 * @brief 音频跳转
 * @param pts 跳转的时间戳（毫秒）
 * @param seek_mode 跳转模式。0 为绝对模式，pts 为非负值；1 为相对模式
 * @return 跳转成功返回 true，失败返回 false
 */
virtual bool seek(uint64_t pts, int seek_mode) = 0;
```

### 2.2 结构体成员注释

```cpp
/**
 * @struct AudioSyncInfo
 * @brief 音频同步信息
 */
struct AudioSyncInfo {
    std::atomic<uint64_t> current_pts{0};  /**< 当前音频帧解码时间戳（ms） */
    std::atomic<uint64_t> next_pts{0};     /**< 下一帧音频解码时间戳（ms） */
    std::atomic<uint32_t> start_time{0};   /**< 流开始的时间 */
};
```

### 2.3 枚举注释

```cpp
/**
 * @enum SyncState
 * @brief 音频同步状态
 *
 * - UNINIT: 音频引擎未初始化
 * - CALIBATING: 音频校准中
 * - SYNCHRONIZED: 音频已同步
 * - AHEAD: 音频时间超前
 * - BEHIND: 音频时间滞后
 * - DISABLE: 未启用同步控制
 * - SYNC_ERROR: 错误状态
 */
enum class SyncState {
    UNINIT,
    CALIBATING,
    SYNCHRONIZED,
    AHEAD,
    BEHIND,
    DISABLE,
    SYNC_ERROR
};
```

## 3. 文件组织

### 3.1 后缀名

C/C++ 文件统一使用：
- **源文件**：`.cpp`
- **头文件**：`.h`

不使用 `.cc` 和 `.hpp`。

### 3.2 目录结构

每个模块遵循三层目录结构：

```text
module/
  include/     -- 公开接口头文件（抽象接口、工厂接口、公共类型）
  internal/    -- 平台实现（impl 细节，不对外暴露）
  src/         -- 源文件
```

**同一个东西在 `include/` 与 `internal/` 下的名字通常不同**：`include/` 放抽象接口（如 `DBAdapter`、`CryptoAdapter`），`internal/` 放平台实现（如 `SQLiteDBAdapter`、`OpenSSLCryptoAdapter`）。这不是命名不一致，不要「统一」掉。完整对照表见根目录 `GLOSSARY.md`。

示例（`client/engine/`）：

```text
engine/
  include/
    AudioEngine.h              -- 抽象接口
    AudioEngineFactory.h       -- 工厂接口
    VideoEngine.h
    VideoEngineFactory.h
  internal/
    AudioEngineWasapiShared.h  -- Windows 平台实现
    VideoEngineVulkan.h        -- Vulkan 平台实现
  src/
    ... (源文件)
```

### 3.3 预编译头

`pch.h` 放在 `common/` 目录，供全局使用。

## 4. 类的设计

### 4.1 成员排列顺序

- **public** 公共成员（公开接口）放在前面
- **private** 私有成员放在后面

```cpp
class AudioEngine {
public:
    virtual bool init() = 0;    // 前面
    virtual bool play() = 0;
    // ...

protected:
    // protected 成员

private:
    // private 成员在最后
};
```

### 4.2 函数定义位置

- 头文件中：仅放声明
- 源文件中：放定义体
- **例外**：模板函数定义须在头文件中实现
- **例外**：简单的 getter 函数（如获取成员变量）可放在类内部

```cpp
// header 中
class VideoEngine {
public:
    int get_width() const { return width; }  // getter 可内联
    virtual bool init() = 0;                  // 声明
};

// src 中
bool VideoEngineVulkan::init() {
    // 定义体
}
```

### 4.3 继承深度限制

如果类的继承超过 **3 代及以上**，应改为类的组合或聚合。

### 4.4 设计原则

类设计必须遵循三大原则：
1. **单一职责原则**：每个类只负责一项功能
2. **开放封闭原则**：对扩展开放，对修改封闭
3. **里氏替换原则**：子类必须能替换父类

### 4.5 构体成员初始化

Struct 成员变量应在结构体内部初始化，默认值尽量为 `0`，**不得重载**结构体的构造函数。

```cpp
// 正确
struct AudioSyncInfo {
    std::atomic<uint64_t> current_pts{0};
    std::atomic<uint64_t> next_pts{0};
    std::atomic<uint32_t> start_time{0};
    std::atomic<uint64_t> duration{0};
};

// 错误 — 不要重载 struct 构造函数
struct AudioSyncInfo {
    AudioSyncInfo() { ... }  // 禁止
};
```

### 4.6 虚析构

**多态基类必须声明虚析构函数**（`virtual ~Base() = default;`）。否则通过基类指针删除派生对象时行为未定义。

```cpp
// 正确
class VideoEngine {
public:
    virtual ~VideoEngine() = default;
    virtual bool init() = 0;
};

// 错误 — 有纯虚函数却没有虚析构
class VideoEngine {
public:
    virtual bool init() = 0;
};
```

> **沿革**：本条由 `cppcoreguidelines-virtual-class-destructor` 强制（见 §0），是规范里唯一一条**新增**的类设计硬约束 —— 它原先不在本规范中，但代码里已经普遍遵守（`VideoEngine`、`AudioEngine` 等都有 `virtual ~...() = default;`），现在把它写下来。

## 5. 函数规范

### 5.1 函数长度

一个函数的代码量**不要超过 100 行**，每个函数应只有单一的功能。

> **注意**：本条由 `readability-function-size`（`LineThreshold: 100`）强制。

### 5.2 API 设计

- 正式编写代码前，优先设计好公共 API 并提交到主分支合并
- 合并后 API 如有变动，须通知所有人
- API 接口设计好后尽量不要变动

## 7. 单元测试

- 模块完成后须编写单元测试
- 测试统一放在 **`test/`** 文件夹中，**按模块分子目录**：

  ```text
  test/
    engine/           # 对应 client/engine/（已落地：test-engine，6 个用例）
    av_sync/          # 对应 client/business/av_sync/（待 av_sync 负责人）
    service/          # 对应 client/service/
    threadpool/       # 对应 vendor/threadpool/
  ```

- 每个子目录放一个 `CMakeLists.txt`；根 `test/CMakeLists.txt` 负责 `find_package(GTest REQUIRED)` + `include(GoogleTest)` + `add_subdirectory(<模块>)`
- 目标命名：`test-<模块>`（当前为 `test-engine`）；测试文件名 `test_<被测对象>.cpp`，用例名 `被测类.行为`
- 使用 **GTest** 框架（来自 vcpkg 的 `test` feature；`find_package(GTest REQUIRED)`，CMake 4.4 的 `FindGTest` 会优先命中 vcpkg 的 `GTestConfig.cmake`）
- 单元测试覆盖率**目标为 80%**，但**这是期望值，不是门禁的阻断条件**：统计工具链已接入（#84，一条命令出报告），数字先记录、不设阈值，见 §7.1。**2026-11-02 实测基线**：行覆盖 8.28%（737 行 / 61 行）、函数覆盖 24.32%（111 / 27）、区域覆盖 6.16%（438 / 27）；其中 `client/engine` 100%，`business/av_sync` 0.00%，`service/Player.cpp` 0.00%

```cpp
// test/engine/test_audio_engine_wasapi_shared.cpp
#include <gtest/gtest.h>
#include "AudioEngineFactory.h"

TEST(AudioEngineWasapiShared, FactoryCreatesEngine) {
    // ...
}
```

### 7.1 覆盖率怎么统计（#84）

一条命令，两个平台各一条（都在仓库根执行）：

```powershell
pwsh -File scripts/build/coverage.ps1      # Windows
```

```bash
bash scripts/build/coverage.sh             # WSL / Linux
```

- **工具链**：编译器自带的 LLVM source-based coverage（`-fprofile-instr-generate -fcoverage-mapping`），由根 `CMakeLists.txt` 的 `PRISM_COVERAGE` 选项打开（默认 `OFF`），只有 `windows-clang-x64-Coverage` / `linux-clang-x64-Coverage` 两个预设会开；构建目录 `build/<Platform>/coverage`，不碰日常 Debug 树。
- **一条命令的链路**：配置 → 构建 → `ctest` → `llvm-profdata merge` → `llvm-cov report`；报告写到 `build/<Platform>/coverage/coverage-report.txt` 并打印到终端。
- **口径**：只统计**项目自己的 C/C++ 源码**（报告按行给出数字，同时附函数 / 区域 / 分支数）；`test/`、`vendor/`、`vcpkg_installed/`、`build/` 一律用同一份正则排除。
  - 统计对象 = 覆盖率构建产出的**全部 `test-*` 可执行文件** + **全部 `libclient-*` 共享库**。共享库即使没有被测试加载也计入（记 0%），所以「未测模块」会以 0% 留在分母里。
  - 静态库只有被上述二进制链接进去时才出现在报告里：`client/business/av_sync` 通过 `libclient-service` 计入（当前 0.00%）。
  - **明确不在当前分母内**：`client/adapter`（静态库，尚无任何测试目标链接）与 `server/*`（尚无测试目标链接/加载）。等对应测试把这些库链进测试目标，它们会自动进入报告；这是口径决定，不是遗漏。

## 8. Git 工作流

**分支命名**：每票一分支，base 永远是 `main`；按类型前缀：

| 类型 | 命名 | 用途 |
|---|---|---|
| 特性 | `feat/<票号>-<短名>` | 实现某张票（例：`feat/54-test-runner`） |
| 修复 | `fix/<票号>-<短名>` | 修 bug |
| 重构 | `refactor/<票号>-<短名>` | 不改变行为的整理 |
| 测试 | `test/<票号>-<短名>` | 只动测试 |
| 文档 | `docs/<短名>` | 纯文档改动 |
| 杂务 | `chore/<短名>` | 门禁 / 构建 / 依赖 |

短名用 kebab-case 英文，写清主题（`chore/format-pp-indent`、`docs/sync-status`），不带人名。历史遗留分支 `pr/<n>`、`Quasar-<n>` 与无票号的 `test/<主题>` 属旧流程，不再新增。

- 开发时**新建分支**进行开发，**不得直接在 main 分支上开发**（规则集已禁止非快进推送与删除 `main`）
- 合并到 main 分支前需提交合并申请（Pull Request）并进行代码审查
- 代码审查中如不符合以上规范则打回修改

**一次改动从提交到合并的完整路径**：

1. 本地 `pre-commit`：staged 的 C/C++ 文件必须过 `clang-format --dry-run --Werror`，文件名不得是 `CmakeLists.txt`。
2. 本地 `pre-push`：先跑 `<平台>-clang-x64-Debug` 构建，成功后对本次推送相对 `main` 改动的 C/C++ 文件跑 clang-tidy；工具版本前缀必须是 `23.1`。
3. 推送并开 PR：标题沿用 `<type>(<scope>): <摘要>`，正文写清改了什么、怎么验证、`Merge Danger`（影响哪些产物/文档）与 `Closes #<票号>`；与 spec 的差异也要写。
4. 服务端检查：GitHub Actions（`.github/workflows/gate.yml`）的六个**必需**检查全绿 —— `hooks-self-test`、`checks-self-test`、`format`、`build-linux-debug`、`tidy`、`ctest`；job 名是规则集（id `15828446`）契约，改名必须同步。
5. 评审与合并：规则集要求 1 条 review；单人仓库只能自审，用 `gh pr merge --merge --admin` 合并（`--admin` 是绕过，会留在 PR 历史里）。规则集允许 merge / squash / rebase，本仓库统一用 **merge commit**，不混用。
6. 收尾：合并时删远端分支；本地 `git switch main && git pull --ff-only`；回对应 issue 留交付说明（完成了什么、验证证据、延后项），未随 `Closes #` 自动关闭的手动 `gh issue close` 并附证据。

**当前执行方式（照实记）**：

- 仓库目前只有 **@xiaofusu123 一名 admin**，其他成员虽在 collaborators 中但尚无提交。
- **GitHub 不允许 PR 作者请求自己 review**，所以单人开发时 PR 实际是**自审自合**：仍然开 PR、仍然写「做了什么 / 为什么 / 不包含 / 审查」四节，但没有人会独立复审。这是当前的事实，不是规范允许的做法。
- 因此「合并前须代码审查」这条**现在无法真正满足**。等有多人同时在提交后恢复互审，并考虑引入 `CODEOWNERS` 做强制指派。
- 门禁（§0）落地后会承担一部分原本靠审查拦的工作（格式、命名、函数长度、文件名大小写）。即便如此，**门禁只是底线，不是审查的替代**。
- **唯一允许的绕过**：一次性批量格式整理可以用 `git commit --no-verify` / `git push --no-verify`，但必须在 PR 描述里说明（见 `AGENTS.md`「未整理的文件与唯一允许的绕过」）。
