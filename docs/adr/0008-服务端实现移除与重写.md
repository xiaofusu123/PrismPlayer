# 0008 服务端实现移除与重写

- 状态：**已接受**（2026-11-23 决策，见「## 决策」）
- 日期：2026-11-23
- 相关：#61、#83、#95、#117、#119、#124、#125、#126、PR #165、`server/**`、`test/server/**`、`vcpkg.json`、`CMakePresets.json`、`scripts/build/verify-build.*`、ADR 0001、ADR 0005、`docs/asyncapi/asyncapi.yaml`

## 背景

**1. 服务端曾有一套完整骨架。** 2026-10-18 的两份文档（`docs/plans/2026-10-18-server-implementation.md`、`docs/specs/2026-10-18-server-implementation-design.md`）定了 Network → Business → Adapter 三层；#147 / #150 之后 `server/` 下 34 个文件全部非空，`Prism-server` 能构建、能进 CI 的 `build-linux-debug`。

**2. 但这条线从未真正闭环。** 服务端只在 Ubuntu 24.04 的 CI 上从零构建过，从未与客户端联调；`test/server/` 只有 `CMakeLists.txt`，没有注册任何用例；#83 的 MySQL 持久化一直停在「计划内未声明」；`server/adapter` 的 `verify_password(password, hash, salt)` 与客户端两参语义不一致（spec #117 决策 23 / 44）；`docs/asyncapi/asyncapi.yaml` 的真源指向 `ServerTypes.h`，也没有契约测试守护。

**3. 分支与主干已经分叉。** PR #165（Quasar18）在 2026-11-09 同时改了 client 与 server 两侧，随后与 main 冲突、连 `pull_request` workflow 都起不来；PR #171 / #172 已把 client 侧接口统一到 `std::chrono::milliseconds`，旧服务端代码即使合并也要再改一轮。

**4. 负责人变更是这次决策的直接触发点。** 2026-11-23 owner 明确「server 改回由我负责」，并决定现有实现整体删除、由 owner 重新写，而不是在旧骨架上继续修补。

## 决策

**Q1 删除范围：整个 `server/` 子树。** 删除 `server/**`（34 个文件，含 `main.cpp` 与三个子模块）与 `test/server/**`；根 `CMakeLists.txt` 去掉 `add_subdirectory(server)`，`test/CMakeLists.txt` 同理。不保留空目录、不保留「先留着以后用」的源码。

**Q2 依赖与预设：去掉 `server` feature。** `vcpkg.json` 的 `server` feature 依赖（asio、ixwebsocket、nlohmann-json、openssl、spdlog）全部是 `client` feature 的子集，删除后安装集不变；六个预设的 `VCPKG_MANIFEST_FEATURES` 从 `client;server;test` / `client;server` 改为 `client;test` / `client`。

**Q3 产物契约：4 个业务产物降为 3 个。** `scripts/build/verify-build.{ps1,sh}` 去掉 `server/Prism-server(.exe)` 的存在性与体积断言，只保留 `client-engine`、`client-av_sync`、`client-service`。CI 的六个必需检查不变；`ctest` 仍为 44 个用例（服务端从未注册用例，删掉不减少数字）。

**Q4 文档按「当前状态」改，历史按日期保留。** 项目框架 / 项目计划书 / 数据流 / 代码规范 / 设计文档里的服务端章节改为「已移除、待重写」的状态陈述，并指向本 ADR；ADR 0001、0005 与 2026-10-18 的 plans / specs 作为历史依据保留。`docs/asyncapi/asyncapi.yaml` 作为重写目标保留，但在 `info.description` 里注明真源文件已删除。

**Q5 issue 归属一并调整。** 服务端相关票（#61、#83、#95、#119、#124、#125）由 owner 接手；#95（多进程 + 真 `Prism-server` 端到端）在重写落地前处于阻塞状态，不应当由 agent 领取。

**Q6 旧的设计约束继续有效。** 重写仍按 Network → Business → Adapter 三层、只做「房间 + 认证 + 消息转发」、不链接 `client/`、目标平台 Ubuntu 24.04（ADR 0001 / 0005 的决策不因删除而失效）。

## 影响

- **构建**：Debug 链接目标从 9 个降到 5 个（`client-engine`、`client-service`、`client-adapter`、`client-av_sync`、`test-engine`）；`Prism-server` 目标不存在，任何仍断言它的脚本 / 文档都会失败（本次已清理）。
- **CI**：`build-linux-debug` 的 verify 只查 client 产物、`prism_player_*` 导出与「不链接 libc++」，无需改判定入口；`ctest` 数字不变。
- **文档**：服务端章节从「已实现」变为「已移除 / 待重写」；`asyncapi.yaml` 保留但真源待重写后落位。
- **可逆性**：删除本身是一个 commit，`git revert` 能把代码拿回来；但 issue 指派与「服务端归 owner」的口径需要人工恢复，故按**一次性决策**对待。
