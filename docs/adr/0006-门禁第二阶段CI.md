# 0006 门禁第二阶段：服务端 CI

- 状态：已接受（**落地中**，落地票 #96 与 #97–#104）
- 日期：2026-10-16
- 相关：`docs/adr/0002-代码门禁.md`（第一阶段的结论不原地改写）、`.github/workflows/gate.yml`、`scripts/ci/setup-linux.sh`、`scripts/checks/`、`AGENTS.md`「代码门禁」

## 背景

ADR 0002 把 CI 列为第二阶段，理由是「CI 要跑起来需要一台能装 msys2 + clang + vcpkg 且带 `CLANG_ROOT` / `VCPKG_ROOT` 的 Windows runner，而这套环境目前只在成员本机存在」。**这条前提已经不成立**：构建在两平台上都被实测可复现并由脚本断言（Windows 与 WSL Ubuntu 24.04.5 各清空重装一次，两个验收脚本各 20/20 通过），依赖安装、预设、产物契约都有可复现口径（见 `docs/markdown/项目框架.md` 7.1）。

而只挂在本机钩子上的门禁有三个结构性缺口：

- 钩子的效力取决于「这台机器装过钩子」与「这次提交没加 `--no-verify`」两件都不出错的事。新克隆、没跑过安装脚本的协作者、以及直接在网页上编辑的改动都不经过门禁；
- 钩子只在**提交者自己的平台**上跑。Server 端的目标平台是 Ubuntu，而 Windows 上的钩子跑的是 `windows-clang-x64-Debug` —— 文件名大小写、缺头文件、Windows-only 假设这些问题仍然要等部署才暴露；
- 每个 PR 上没有任何机器结论。在这个事实上是自审的仓库里，评审无从区分「这个改动确实构建过」和「这个改动只是看起来没问题」。

仓库是公开仓库（Actions 对标准 runner 不计费），所以这一阶段的成本约束是**等待时间**与**信噪比**，不是额度。

## 决策

**1. 载体：服务端 CI，只跑 `ubuntu-24.04` 上的 `linux-clang-x64-Debug`（manifest features `client;server;test`）。**

Windows runner 与 Release 预设不在这一阶段。Server 的目标平台就是 Ubuntu，CI 对它最有说服力；Windows 口径已由本机钩子覆盖。本地钩子保留为**快反馈层**（提交前几秒），CI 是**不可绕过层**（换机器、换事件、换人都不失效）。

**2. 判定逻辑只写一遍：从钩子里抽成 `scripts/checks/` 下的可复用检查入口，接受一个「变更范围」参数。**

范围参数只有三种形态：`staged`（暂存内容，`pre-commit` 用）、`<rev>`（`<rev>...HEAD`，`pre-push` 用）、`<a>...<b>`（任意区间），外加 `ci`（从 GitHub Actions 的环境里解析出 `base...head`，让 workflow 不必在 YAML 里判断事件类型）。入口有三个：格式检查、静态检查、产物契约断言（后者复用既有的 `scripts/verify-build.sh`，不重新发明）。

**workflow 只做编排** —— 装工具链、还原缓存、按预设配置与构建、调用入口。判定逻辑一律不写进 YAML，否则本地与 CI 必然各自漂移，而那正是 ADR 0002「规范纯靠自觉」的同一个教训。

**3. 只查本次变更范围，不做全仓检查。**

仓库里多数 C/C++ 文件还没跑过 `clang-format`（既有决策：不做全仓一次性重排，碰到哪个整理哪个）。全仓检查会让 CI 从第一天起常年飘红，而这正是 ADR 0002 明确要避免的结果。同一条理由适用于 clang-tidy 已启用的规则（#85 在逐条扩）：基线清零只对当时的编译单元成立，全仓扫描会引入历史噪声。

**4. 工具链与本地同源，并且钉版本前缀。**

clang / clang-format / clang-tidy 来自 `apt.llvm.org` 的 `noble-23` 仓（与本机 WSL 实测的那一套同源），cmake 4.x 来自 Kitware 仓（Ubuntu 24.04 自带的 3.28 不够），ninja 由 `scripts/ci/setup-linux.sh` 的 `system` 组件**显式安装**（构建器不能指望镜像碰巧自带，见 #99 的产物契约断言）。**版本前缀 `23.1` 不符即失败退出**，不出现「runner 自带 clang-18 静默通过」这种假绿 —— 这一判定直接复用门禁自己的 `prism_require_tool`，CI 与本机对工具链的要求只有一份实现。

干净 runner 上要装什么，**单一事实来源是 `scripts/ci/setup-linux.sh`**（workflow 只调用它，清单不在 YAML 里重复一遍）：

| 组件 | 内容 | 为什么 |
|---|---|---|
| `llvm` | `clang` / `clang++` / `clang-format` / `clang-tidy` / `clang-tools` / `lld` / `libclang-rt-dev` 的 23.1.x 包（apt.llvm.org `noble-23` 仓） | 与成员本机同源；版本前缀由 `scripts/checks/lib.sh` 钉死，不符即失败退出 |
| `cmake` | cmake 4.x（Kitware 仓，装之前先按 `cmake --version` 判断是否已 ≥4） | Ubuntu 24.04 自带 3.28，低于本仓库实测口径（Windows 4.3.2 / WSL 4.4.4） |
| `system` | `ninja-build`、`pkg-config`、`binutils`（产物验收要用 `objdump`）、`nasm` / `yasm`、`autoconf` / `automake` / `libtool` / `libltdl-dev`、X11 一族（`libx11-dev` `libxext-dev` `libxrandr-dev` `libxinerama-dev` `libxcursor-dev` `libxi-dev` `libxfixes-dev` `libxss-dev` `libxxf86vm-dev` `libxcb1-dev` `libx11-xcb-dev`）、`libgl-dev` / `libglu1-mesa-dev` / `libegl-dev` / `mesa-common-dev`、`libvulkan-dev`、`libwayland-dev` / `wayland-protocols` / `libxkbcommon-dev`、`libdrm-dev`、`libasound2-dev`、`python3` | glfw3 / vulkan / ffmpeg 的 vcpkg port 在 Linux 侧要这些开发包（风险清单第①条）。整份清单在 WSL Ubuntu 24.04.5 上逐个用 `apt-get install -s` 验过包名可解析，不靠 runner 镜像碰巧自带 |
| `vcpkg` | 按 `vcpkg-configuration.json` 的 `default-registry.baseline` 浅取一份 vcpkg 到 `$VCPKG_ROOT`（CI 上 `/home/runner/vcpkg`）并 `bootstrap-vcpkg.sh -disableMetrics` | 依赖获取只有这一条路：**不用系统 ffmpeg / 系统 Vulkan 替代 vcpkg**，否则放弃「同一 baseline ⇒ 同一组产物」（决策 5） |

**5. vcpkg 二进制缓存是核心杠杆，不是优化项。**

干净 runner 上 ffmpeg / glfw3 / vulkan 等依赖要从源码编译（本机 Linux 侧实测一次性约 14 分钟），而项目自身编译只要约 27 秒。缓存键 = **vcpkg baseline + manifest 内容哈希 + triplet + runner 镜像 + clang 版本前缀**；键的构成就是「CI 什么时候会变慢」的答案。依赖获取仍走仓库内既有的工具链转发脚本与固定 baseline，**不用系统 ffmpeg / 系统 Vulkan 替代 vcpkg** —— 那会放弃「同一 baseline ⇒ 同一组产物」这条可复现口径。

**6. job 名即契约。**

`main` 的规则集把这些 job 名设成必需状态检查，因此改名必须同步规则集，否则必需检查会静默失效。草稿 PR 照样跑检查（便于自查），必需检查只在非草稿时生效；`--admin` 仍然能合并 —— 单人仓库 + 规则集要求 1 条 review 只能自审自合。CI 的价值不是「物理上不能绕过」，而是「每一次绕过都留下一次机器红/绿记录」。

**7. `ctest` 是接入点，不是门禁。**

`test/` 还没有注册任何测试用例之前，这个 job 明确 SKIP 并写明原因，不假装绿。等测试跑道（#54）落地、根构建里出现 `add_test()` 之后，同一个 job 自动变成真检查，不需要重新设计 CI。覆盖率（#84）与性能基准（#94）在这套 CI 上的位置由那两张票自己决定，本 ADR 不预设。

## 后果

**正面**：

- 「CI 说绿」与「本机说红」在结构上不可能出现：两边调用同一份入口。
- 坏改动进不了 `main`（除非显式 `--admin`），而且绕过这件事在 PR 历史里可见。
- Server 的目标平台在推送当天就被真实构建一遍，`CmakeLists.txt` 这类平台相关错误不再等部署才暴露。
- 「构建成功」这句话有可核对的证据：既有的产物契约断言（体积阈值、≥32 个 `prism_player_*` 导出、不含 libc++）在 CI 上跑一遍。

**负面 / 已知缺口**：

- **依赖编译是唯一真正的成本**。缓存未命中时一次 CI 运行落在十几分钟量级；命中后落在几分钟量级。缓存键里任何一个成分变化都会触发一次冷编译 —— 这是设计意图，不是故障。
- **`tidy` job 自己按同一预设配置一次**，而不是把构建 job 的 `compile_commands.json` 用 artifact 传过去。原因是依赖头文件树（本机实测 `vcpkg_installed` 537 MB）比数据库本身大两个数量级，传它不划算；顺序上仍由 `needs: build-linux-debug` 保证，且入口在数据库缺失或加载失败时显式拦下，不会得到「什么都没查到的假绿」。
- **Windows runner 与 Release 预设在 CI 上仍然缺席**。本机钩子覆盖 Windows Debug，Release 靠发布前的本机构建。
- **全仓格式与全仓静态检查仍然不做**。存量未格式化文件靠「碰到哪个整理哪个」逐步逼近。
- 钩子仍然可以被 `--no-verify` 绕过，但这条路径现在有 CI 兜底。

## 备选方案

- **Windows runner**：能覆盖 `x64-mingw-dynamic` 这套依赖，但要在干净 Windows runner 上装 msys2 + mingw64 clang 23.1.3 + vcpkg，本机实测该 triplet 全量重装 26 分钟且失败过一次。放弃于本阶段：Windows 口径已由本机钩子覆盖，收益与成本不成比例。
- **容器化 / 自托管 runner**：口径更可控，但把「维护一台机器」换成了「维护一套镜像」，而当前瓶颈是首次依赖编译，不是环境漂移。放弃。
- **用系统库（`apt install` 的 ffmpeg / vulkan）替代 vcpkg**：能把冷启动从十几分钟压到一两分钟。放弃原因是它会放弃「同一 baseline ⇒ 同一组产物」，让 CI 的构建结果与成员本机不再是同一个东西 —— 那正是这一阶段要修的问题。
- **全仓格式 / 全仓静态检查**：最彻底。放弃原因见决策 3，与 ADR 0002 决策 2 的结论一致。
- **把 `compile_commands.json` 用 artifact 从构建 job 传到 `tidy` job**：少一次配置。放弃原因是依赖头文件树必须一起存在才分析得准，只传数据库会得到满屏「file not found」，见「后果」。
- **让 `ctest` job 在没有测试时直接删掉**：少一个空 job。放弃原因是那样 #54 落地后还得重新设计编排，而「明确 SKIP」本身就是一条比「没有这个 job」更诚实的信息。
