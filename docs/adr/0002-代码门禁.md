# 0002 代码门禁

- 状态：已接受（**已落地**，落地票 #64；钩子、`.clang-format`、`.clang-tidy` 均在仓库内，三条规则的基线已清零）
- 日期：2026-10-09
- 相关：`docs/markdown/代码规范.md` §1–§5、`docs/agents/triage-labels.md`

## 背景

`docs/markdown/代码规范.md` 写了 9 节规范（命名、注释、文件组织、类设计、函数长度、日志、单测、Git 工作流），但仓库里**没有任何自动检查**：

- 无 `.clang-format`、无 `.clang-tidy`、无 `.editorconfig`；
- `.git/hooks/` 里除 `*.sample` 外为空，无 `.githooks/`、无 `.pre-commit-config.yaml`；
- 无 `.github/`、无任何 CI 配置。

后果是规范纯靠自觉，且**已经失守**：`server/` 与 `vendor/` 下曾有 6 个文件被命名为 `CmakeLists.txt`（小写 `m`），在大小写敏感的文件系统上 `add_subdirectory()` 根本找不到它们 —— 而 Server 端的目标平台恰恰是 Ubuntu。（**`server/` 下 3 个已于 2026-10-11 改为大写**；`vendor/` 下剩余的仍是小写，已决定暂不处理。）此外 `docs/markdown/代码规范.md` §8 写了「不得直接在 `main` 开发」，实际上仓库长期只有一个分支在工作。

同时有一个反向约束：**门禁必须以「能编译」为前提**。这条前提**已经成立**（2026-10-09 晚 / 2026-10-11 两次补验）：vcpkg 安装树完整（23 个包、与 vcpkg 自己的 `.list` 比对 0 缺文件）、`cmake --build --preset windows-clang-x64-Debug` 返回 `ninja: no work to do.`（exit 0）、`libclient-service.dll` 导出全部 32 个 C API，入口脚本也已重写并搬到 `scripts/`（4 配置 + 4 构建预设，各自 `binaryDir`）。本 ADR 立项时写的「安装树只剩 `asio`」「`build.sh` 是 5 行空壳」「预设名写成 `windows-clang-x64-Releasee`」**均已作废**。

## 决策

**1. 载体：本地 Git hooks，不引入 CI。**

提交 `.githooks/`（`pre-commit`、`pre-push`）+ `.clang-format` + `.clang-tidy`，用 `git config core.hooksPath .githooks` 启用。不上 GitHub Actions。

理由：CI 要跑起来需要一台能装 msys2 + clang + vcpkg 且带 `CLANG_ROOT` / `VCPKG_ROOT` 的 Windows runner，而这套环境目前只在成员本机存在；先修好本机基线、让门禁真正跑起来，比先搭一个跑不起来的 CI 更有价值。**CI 列为第二阶段**，等构建可复现之后再评估。

> **2026-10-16 更新（只加指针，本决策的结论不在此处改写）**：第二阶段已启动 —— CI 的载体、平台与预设范围见 `docs/adr/0006-门禁第二阶段CI.md`，本地钩子保留为**快反馈层**，CI 是**不可绕过层**。上面那条「只在成员本机存在」的前提已经由两平台的可复现构建消掉（`docs/markdown/项目框架.md` 7.1）。

**2. 深度：clang-format 全量 + clang-tidy 只开 3 条规则。**

`.clang-format`：

```yaml
BasedOnStyle: LLVM
IndentWidth: 4
ColumnLimit: 100
PointerAlignment: Left
BreakBeforeBraces: Attach
NamespaceIndentation: None
AllowShortFunctionsOnASingleLine: Inline
```

`ColumnLimit: 100` 是新定的值 —— 规范 §5.1 只约束了函数 ≤100 行，从未写过行宽。

`.clang-tidy`：**只启用三条**，且都设 `WarningsAsErrors`：

| 规则 | 参数 | 对应规范 |
|---|---|---|
| `readability-identifier-naming` | 按 §1.1 / §1.2 / §1.3 配 Case（类型 PascalCase、函数与变量 snake_case、宏与常量全大写） | §1.1–1.3 |
| `readability-function-size` | `LineThreshold: 100` | §5.1 |
| `cppcoreguidelines-virtual-class-destructor` | — | §4.3 / §4.4 |

**为什么只开这三条**：clang-tidy 的注释覆盖率、魔法数字、`modernize-*` 一类规则在现有代码上会一次炸出几百条告警。门禁一旦让人「每次提交都要滚过一屏红字」，结果一定是全体加 `--no-verify`，等于没有门禁。以后**按「先加检查 → 先清零 → 再启用」逐条加**。

**3. pre-commit 与 pre-push 的职责划分。**

- `pre-commit`：对 staged 的 `*.c` / `*.cc` / `*.cpp` / `*.cxx` / `*.h` / `*.hh` / `*.hpp` / `*.hxx` 跑 `clang-format --dry-run --Werror`；再加一条「文件名不得为 `CmakeLists.txt`」的防回归检查（见 #52）。**该检查必须对 `vendor/**` 例外**（`vendor/` 下仍有 3 个小写 `CmakeLists.txt`，已决定暂不处理；`vendor/` 不参与根构建，见 #67 与 #39 决策 29）。**这个例外只到文件名检查为止**：`vendor/` 下的 C/C++ 文件与别处一样要过 clang-format —— `AGENTS.md` 里「只做格式检查，不受 `CmakeLists.txt` 重命名检查约束」说的就是这一层。文件名与格式的判定对象都是 **index 里的内容**（`git show :<path>`），所以部分 stage 的文件按真正要提交的那份判定，未 staged 的改动完全不受影响；文件清单取 `git diff --cached --diff-filter=ACMR`，`git mv`（index 里记为 `R100`）同样会被检查到。
- `pre-commit` **不跑 clang-tidy**：它需要 `compile_commands.json`（构建现在能产出，但门禁尚未落地，且只要 staged 了源文件这份文件就代表不了当前改动），而且慢到开发者会直接绕过。
- `pre-push`：先跑 `cmake --build --preset <平台>-clang-x64-Debug`（Windows/Linux 各自取本平台的 Debug 预设）。**不跑 `ctest`**（列第二阶段）、**不跑 Release 预设**（耗时翻倍而收益低）。
- `pre-push` **在构建成功之后**跑 clang-tidy，范围是「本次推送相对默认分支改动的 C/C++ 文件」（取 `git merge-base` 与 `main` 的分叉点；改动的头文件沿 `#include` 链向上找到编译单元，最多 3 层，本仓库实测深度为 2）。决策 2 的三条规则此前没有落点，这里补上：**执行点就是 `pre-push`，不是 `pre-commit`**。没有 C/C++ 改动时直接跳过，不产生额外耗时。构建产出的 `compile_commands.json` 是这一步的输入，所以顺序不能颠倒。覆盖率不假装：3 层内没有被任何编译单元引用的改动文件会被明确列出。
- 编译数据库由 `CMakePresets.json` 的 `CMAKE_EXPORT_COMPILE_COMMANDS: ON`（两个 hidden 基预设）在配置阶段产出；`pre-push` 发现它缺失（例如旧构建树）时会自己跑一次 `cmake --preset` 自愈。
- 耗时：热构建树（增量构建 + 编译数据库就绪）实测见 `AGENTS.md`，预算上限 15 分钟；冷配置要装 vcpkg 依赖，会明显更久。

**4. 安装方式**：提交 `scripts/install-hooks.ps1`（Windows）与 `scripts/install-hooks.sh`（WSL/Linux），内容都是 `git config core.hooksPath .githooks` 并读回校验确实生效；并把这一步写进 `AGENTS.md` 的代码门禁一节，让新克隆能一次配好。hook 脚本统一用 `#!/bin/sh`，由 Git for Windows 自带的 bash 执行，**不依赖 cmd 或 PowerShell**（成员机器上 cmd 与 Git Bash 的行为不一致，这是最容易踩的坑）。`.gitattributes` 里 `.githooks/* text eol=lf` 是这栋楼的地基：钩子没有扩展名，Windows 检出若变 CRLF，`#!/bin/sh` 直接 bad interpreter，连版本检查都跑不到。

**5. 允许 `--no-verify`，但限一种情况**：格式批量整理（例如初次引入 clang-format 时的一次性重排）需要单独一次提交、与本就是一次性的提交合并会污染历史。使用者必须在 PR 描述里说明这次跳过了什么。日常提交不允许。违规靠 PR 审查拦 —— 这也是为什么 §8 的「合并前须提交合并申请并代码审查」必须真的执行。

**6. 工具版本钉死为 `23.1.3`**（2026-10-12 修订，原为 `22.1.8`）。`clang-format` / `clang-tidy` 只要版本不同，格式化结果就会在成员之间来回抖动（A 格式化、B 提交时又改回去）。hook 的第一件事就是比对版本前缀，不匹配直接报错退出。`CMakePresets.json` 已经依赖机器级的 `CLANG_ROOT`（默认 `D:\Program\App\msys64\mingw64\bin`，2026-10-12 起由 `clang64\bin` 迁来），版本钉死在同一个变量背后。版本随工具链迁移而变的原因见 `docs/markdown/项目框架.md` 7.1：clang64 的 libc++ 与 vcpkg（GCC / libstdc++）ABI 不一致，Windows 构建必须用 mingw64 的 clang。WSL（Ubuntu 24.04.5）侧的 `clang` / `clang-format` / `clang-tidy` 都是 `23.1.2`，与 Windows 的 `23.1.3` 只差补丁位，前缀 `23.1` 相同，因此 hook 的版本前缀比对在两个平台上都能通过。

## 后果

**正面**：格式与三条最硬的规范变成可机检；`CmakeLists.txt` 这类平台相关错误不再靠人去 Ubuntu 上才发现。

**负面 / 已知缺口**：

- **表达不了的部分仍然靠自觉**：clang-format 管不到命名、目录结构、Doxygen 注释格式、类设计、单元测试存在性。规范 §3.1「禁用 `.cc` / `.hpp`」也没有落点 —— 现有 `.hpp` / `.cc` 是 `vendor/` 与 Flutter 生成的文件，一刀切会误伤（门禁只对 `.cc` / `.hpp` 做**格式**检查，不拒绝这个扩展名）。
- clang-tidy 三条规则的**首次全量扫描已经完成**（#69）：改造前用 release 编译数据库扫 11 个编译单元，共 8 处诊断、2 个标识符（`client/engine/include/VideoEngine.h` 的 `RENDER_RESULT_HANDLE` 报 `invalid case style for typedef`、`client/common/API.h` 的 `#define _API` 报 `invalid case style for macro definition`），清零方式是**改代码**（`RENDER_RESULT_HANDLE` → `RenderResultHandle`、`_API` → `PRISM_API`，后者以「下划线+大写」开头本就属于保留给实现的标识符），改造后同一套扫描为 **0 处诊断**。三条规则中 `readability-function-size` 与 `cppcoreguidelines-virtual-class-destructor` 本来就没有命中，说明这两个维度现有代码是干净的。
- `pre-push` 挡在 push 前面意味着**推送前必须能完整构建**，开发者本地改了一半就推不了 —— 这是刻意的，但会在构建本来就慢的时候被抱怨。
- **覆盖率 >80%（§7）不进门禁**。它是 PR 审查的期望值，不是阻断条件（理由见 #43 的结论：真正有实现的代码只有三处，硬卡覆盖率只会逼出形式化的空测试）。

## 备选方案

- **GitHub Actions CI**：对多平台（尤其是 Server 的 Ubuntu 目标）更有说服力，且无法被 `--no-verify` 绕过。放弃于第一阶段的原因是仓库当前构建不可复现，CI 会长期一片红，反而让人学会忽略它。第二阶段重新评估。**（2026-10-16：重新评估的结论是启动 —— 见 `docs/adr/0006-门禁第二阶段CI.md`。）**
- **`pre-commit` 框架（Python）**：生态成熟、hook 管理方便。放弃原因是它要求每个成员装 Python 环境，而这个项目的工具链已经够重（MSYS2 + clang + vcpkg + Flutter）。
- **只靠 code review 不设门禁**：仓库长期只有一个人在工作，review 事实上是自审，没有第二双眼睛能兜住格式漂移。
- **全量 clang-tidy（`modernize-*` + `cppcoreguidelines-*` 全套）**：一次引入几百条告警，必然被绕过，见决策 2。
- **把 ctest 放进 `pre-push`**：等 `test/` 恢复、全量测试耗时可测之后再决定（#43 / #54）。
