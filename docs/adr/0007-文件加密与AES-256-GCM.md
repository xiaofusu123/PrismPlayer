# 0007 文件加密与 AES-256-GCM 的范围

- 状态：**已接受**（2026-11-10 决策，见「## 决策」）
- 日期：2026-11-10
- 相关：#117（决策 24）、#82（决策 43）、#122、PR #159、`client/adapter/include/CryptoAdapter.h`、`docs/markdown/API接口文档.md` §4.5、`docs/markdown/设计文档.md` §9、ADR 0005

## 背景

**1. 接口从 #82 起就声明了文件加密。** `client/adapter/include/CryptoAdapter.h` 不只声明口令哈希，还声明了四个 AES-256-GCM 方法：`encrypt_file` / `decrypt_file`（:61, :72）与 `encrypt_buffer` / `decrypt_buffer`（:83, :94），密钥约定为 32 字节。

**2. 但两张 spec 都明令不做。** #82 决策 43 与 Out of Scope：「端到端文件加密（AES-256-GCM）与 WebSocket TLS 不做」；#117 决策 24：「不引入 AES-GCM 代码」，#122 只做口令自描述串与跨侧夹具。**本 ADR 的决策取代这两条。**

**3. 现状却是「接口在、实现有、票面说不做」。** PR #159 已经实现了这四个方法（`OpenSSLCryptoAdapter.cpp`），并写了文件回环、错密钥、篡改、跨 64 KiB 边界的用例。评审结论是：该实现**越界**，但删掉又会留下四个空壳方法，所以需要一次明确的产品/安全决策，而不是在 PR 里默认保留或默认删除。

**4. 文档已经超前于决策。** `API接口文档.md:770` 写「基于 OpenSSL 实现 SHA-256 哈希和 AES-256-GCM 加解密」，:776-779 逐条列出了四个方法；`设计文档.md:431` 则把「文件传输」标成「端到端加密（计划）」。同一能力在文档里既是「已实现」又是「计划」，是因为从来没有决定过它到底做不做。

**5. 真正缺的是密钥与边界的决策，不是代码。** 「用 AES-256-GCM」本身没有争议；没定的是：密钥从哪来、加密哪一段链路、和 TLS/wss 是什么关系、大文件怎么分块、失败时如何保证不破坏原文件。

## 决策

2026-11-10 经 grilling 逐轮决策，Q1–Q7 结论如下。本决策**取代** #82 决策 43 与 #117 决策 24（「不做 AES-GCM」）。

- **Q1 内容层加密：做。** 范围是全链路——音视频/媒体数据、客户端落盘、服务端（登记「要做」，细节随 #83）与通信。算法按设备硬件加速在 **AES-256-GCM** 与 **ChaCha20-Poly1305** 之间选择（两者密钥 32 B、nonce 96 bit，OpenSSL EVP 均支持，无新依赖）。

- **Q2 密钥来源与生命周期：分场景混合。**
  - 媒体 E2E（P2P 直传）：**房间对称密钥**，经信令（已走 TLS/wss）下发，房间内成员共享；每文件随机 96-bit IV。
  - 客户端落盘：**用户口令 KDF 派生**（复用 #122 口令自描述串），密钥不落盘。
  - 服务端：随 #83 另定。

- **Q3 文件格式：分块 AEAD + 头部元数据。**
  - 头：magic + 版本号 + cipher ID（区分 AES-256-GCM / ChaCha20-Poly1305）+ 参数。
  - 体：固定 64 KiB 明文块，每块 `[明文块长 + 96-bit IV + 密文 + 16 B tag]`。

- **Q4 大文件与失败语义。**
  - 流式分块加密，不整块进内存；输出先写**临时文件**再**原子 rename**；**`input != output` 硬校验**。
  - **截断 / 篡改 / 错密钥必须失败**：任一块 tag 校验失败即整体失败并删除临时文件。
  - 顺带修 PR #159 两处缺陷（`while(in)` 把读错误当 EOF；`trunc` 打开未校验 `input != output`）。

- **Q5 与 TLS 的边界。** 信令 / HTTP / WebSocket 只靠 TLS/wss（ADR 0005），**不叠加应用层加密**；内容层加密只针对数据/文件链路——尤其 P2P 直传（ADR 0005 未给 P2P 配 TLS）。

- **Q6 接口归属：拆出独立的 `FileCipher`。**
  - `FileCipher`（接口）/ `OpenSSLFileCipher`（实现）承载 `encrypt_file`/`decrypt_file` + 分块格式 + 临时文件 + 原子替换，命名沿用 `CryptoAdapter`/`OpenSSLCryptoAdapter` 惯例。
  - `CryptoAdapter` 保留口令哈希 + `encrypt_buffer`/`decrypt_buffer`（AEAD 原语，加 cipher 选择）。

- **Q7 范围与票号。**
  - **回退 PR #159 中越界的文件加密实现**（保留其 SQLiteDBAdapter / ASIONetworkAdapter 与口令哈希部分）。
  - **开新票**「FileCipher 分块 AEAD + 临时文件/原子替换 + 修两缺陷」；`CryptoAdapter` 的 cipher 选择并入此票。
  - 房间密钥信令字段挂 #111/#117；客户端落盘挂 #122。
  - 实现票**不排进当前阶段**，等 P2P 直传动工再排期；本阶段产出为本文档定稿。

- **算法选择信号（Q1/Q3 派生）。** 运行时探测（x86 CPUID 的 AES 位 / ARM `getauxval` HWCAP）+ 文件头 cipher ID + P2P 握手协商。

## 后果

按 Q1「做」的结论：

- 需要先落地密钥分发（房间密钥进信令协议，挂 #111/#117）与跨侧口令（#122），再写 `FileCipher` 代码；这是一张独立票的工作量，不能塞进 Adapter 的 CRUD 票里顺带完成。
- 测试必须覆盖：篡改、截断、错密钥、空文件、大文件分块、输出不覆盖输入、重复加密的随机性、双算法（AES-256-GCM / ChaCha20-Poly1305）互操作。
- 服务端敏感字段落盘加密已登记为「要做」，字段清单与实现票等 #83 MySQL 落地后单独开。

## 备选方案（已否决）

- **只保留接口、明确不做**：空壳方法会一直让读者以为能力存在，且与 `设计文档.md` §9「端到端加密」的承诺冲突。
- **保留 PR #159 的实现、直接接受**：等于用代码替 spec 做决定，跳过密钥来源与格式设计；且实现有截断/覆盖输入缺陷。
- **只做本地静态加密（B）**：解决不了「服务端/中转方看到明文」，与「端到端」不是一回事。
- **信封加密（每文件随机密钥 + 授权）**：前向保密更强，但要引入非对称密钥管理（ECDH/RSA），量更大，作为后续增强单独立项。
- **先做 TLS/wss、E2E 延后**：本决策选择了做 E2E，但仍遵循「信令只靠 TLS、内容层加密只在数据/文件链路」的边界。
